# INSOFT 平台部署架构说明

版本：v2.0　　更新日期：2026-11-05　　适用对象：运维与架构人员

## 一、整体拓扑

平台由三部分组成：

1. **两个前端单页应用**：管理/搭建端（默认 3001 端口）和终端用户端（默认 4001 端口，base 路径 /workspace）。
   两者共用同一套后端 API，只是 API 前缀不同。
2. **后端服务**：FastAPI 提供 HTTP 接口（默认 7860 端口），Celery Worker 处理异步任务
   （知识解析、OCR、工作流执行），Celery Beat 负责定时任务，Linsight Worker 是独立的 Agent 执行进程。
3. **六类存储**：
   - MySQL / DM8：业务数据（支持国产达梦数据库）
   - Redis：缓存 + Celery 消息队列
   - Milvus：向量检索（密集召回）
   - Elasticsearch：全文检索（稀疏召回）
   - MinIO：对象存储（上传文件 + Milvus segment）
   - OpenFGA：权限（ReBAC 关系模型）

## 二、检索链路

知识库检索采用**双路召回 + 融合排序**：

1. 用户提问先经过 query 改写和意图识别。
2. 密集召回：query embedding 后在 Milvus 里做 ANN 检索。
3. 稀疏召回：同一 query 在 Elasticsearch 里做 BM25 检索。
4. 两路结果按融合分数排序，取 Top-K。
5. Top-K 结果作为上下文拼装进 prompt，交给大模型生成带引用的回答。

因此知识库效果依赖 embedding 模型质量；换 embedding 模型后需要重建索引。

## 三、多租户

多租户是部署级开关（`config.yaml` 中 `multi_tenant.enabled`），默认关闭。
开启后需要执行数据库迁移，且已运行的实例需重启生效。关闭状态下所有用户属于同一个默认租户。

租户隔离通过 ContextVar 自动注入实现，业务代码无需显式传 tenant_id。
权限检查统一走 PermissionService → OpenFGA。

## 四、部署方式

| 方式 | 适用场景 | 说明 |
|---|---|---|
| Docker Compose | 中小规模、快速验证 | 单机，7 个中间件容器 + 后端 |
| Kubernetes | 生产、大规模 | 需配套 runtime-manager 做应用沙箱调度 |
| 源码运行 | 本地开发调试 | 宿主机跑 Python 进程，中间件用容器 |

源码运行时的最小中间件集合：mysql、redis、elasticsearch、etcd、minio、milvus、openfga。

## 五、监控与日志

- 应用日志：`data/bisheng.log`（loguru 滚动）
- 统计日志：`data/statistic.log`
- 健康检查：`GET /health`（根路径，不在 /api/v1 下）
- 中间件：ES `GET :9200/_cluster/health`，OpenFGA `GET :8080/healthz`
